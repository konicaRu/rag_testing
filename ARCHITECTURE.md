# Архитектура rag_testing

Первоначальный проект архитектуры от 14 октября 2026; состояние уточнено 19 октября 2026. Ниже разделены существующий контур Golden Dataset и будущие компоненты.

## Реализованный контур Golden Dataset

`rag_a3` (исходные Markdown, только чтение) → `golden_dataset_project/corpus_manifest.csv` (200 ссылок с SHA-256) → существующий `notebooks/01_golden_dataset.ipynb` → ручной анализ пользователем в JupyterLab.

Окружение находится в `rag_testing/.venv`, kernel — **A3 Golden Dataset**. Рабочая директория Notebook — `golden_dataset_project/notebooks`. `config.yaml` разрешает пути относительно своего каталога: корень исходников `../../rag_a3`, выход `golden_dataset`. Рабочий RAG не изменяется. Старое `rag_a3/rag_evaluation` сохранено как прежняя копия.

Корпус фиксирован: G001–G200, 194 Confluence и 6 ручных документов, версия `a3-golden-v1-756cab840ac23189`. ID не пересоздаются из путей при переносе. SHA-256 считается по исходным байтам. Перенос manifest не меняет версию корпуса. Статусы 174 `unknown` и 26 `possibly_outdated` сохранены; `unknown` не означает подтверждённую актуальность.

## Следующий эксперимент: запланирован, ещё не реализован

Бизнес-словарь трёх сущностей → 15–20 документов → локальное выделение фрагментов → проверка локального подключения LM Studio → структурированная оценка LLM → проверка точных доказательств и сравнение с ручной оценкой.

Сущности: `active_subscription`, `system_subscription`, `notification`. Теги `related_entities` служат исходной гипотезой, а не семантическим доказательством. Релевантность 0–3 и соответствие определению оцениваются отдельно. Схема и ограничения — в [README Golden Dataset](golden_dataset_project/README_GOLDEN_DATASET.md#текущий-прогресс-и-эксперимент).

Qwen3-8B, Nemotron3 Nano 4B и BGE-M3 ранее найдены на диске; доступность и API ID в LM Studio не проверены. Облачного fallback нет. BM25, векторный индекс, Ragas, Knowledge Graph, генератор вопросов и адаптер оценки ниже остаются будущими компонентами, а не выполненными работами.

## Компоненты первоначального целевого проекта

| Компонент | Вход | Выход |
|---|---|---|
| Jupyter Notebook в VS Code | Настройки пользователя | Последовательный запуск и таблицы |
| Читатель корпуса | Локальные Markdown | Документы с метаданными |
| Подготовка текста | Документы | Фрагменты, ID, группы дублей |
| Индексатор | Фрагменты + LM Studio embeddings | BM25 и отдельный векторный кеш |
| Подборщик | Тема | Объединённый рейтинг кандидатов |
| Генератор тестов | Утверждённые фрагменты + отдельная LLM | Черновые вопросы, ответы, цитаты |
| Проверка человеком | Черновики и тексты | Версия утверждённого эталона |
| Адаптер RAG | Вопросы | Ответы, источники и контекст |
| Оценщик | Выдача + эталон | Метрики и отчёты |

Прямой зависимости от NotebookLM нет. Ragas — планируемая интеграция для генерации и оценки, а не установленная обязательная зависимость.

## Поток данных

Тема → BM25 + Giga → кандидаты → утверждение материалов → генерация тестов → проверка эталона → API RAG → сохранение выдачи → вычисление метрик.

Подготовка эталона и запуск тестируемого RAG разделены. Источники читаем; изменения исходного rag_a3 не входят в первый этап.

## Корпус и идентификаторы

Текущий Golden Dataset использует только `confluence_pages/<продукт>/*.md` и `local_docs/other/*.md` по manifest; attachments, чанки и output_ranked исключены. Следующие профили сохранены для будущего общего тестирования RAG, не для расширения текущей выборки:
- serving_corpus: local_docs + output_ranked + используемые эталоны с правилами загрузки чата;
- source_corpus: исходные локальные материалы + Confluence для исследования потерь предварительного отбора.

Не смешиваем эти профили в одном recall без явного обозначения области оценки.

В текущем корпусе document_id — сохранённый G001–G200. Для будущих иных профилей первоначально предлагался ID из нормализованного пути; это не основание переименовывать существующие G-ID. Будущий chunk_id должен включать document_id, границы раздела и хеш текста. Изменения корпуса требуют согласованного версионирования, а не молчаливой замены хешей.

Если единица оценки RAG — полный файл, сопоставляем фрагменты разметки с ID файла для документных метрик. Нельзя сравнивать чанк и целый документ как одинаковые единицы без адаптации. Для смыслового покрытия используем фактический контекст генерации.

Дубли объединяем по установленному правилу и сохраняем все исходные пути. Не используем только basename: разные файлы могут иметь одно имя.

## Кеш и воспроизводимость

Ключ кеша включает модель, сборку/версию, параметры обработки, хеш текста и размерность. Новый embedder требует собственного индекса. Запросы и документы кодируются одной моделью с корректными разными инструкциями.

Настройки запуска: источники, корпус, модель, chunking, BM25, fusion, K, промпты, температуры, версии зависимостей и эталона. Результаты сравниваются на одинаковых версиях.

Для 700 документов достаточно локального BM25 и матрицы векторов; отдельный сервер векторной БД в первом варианте не планируется. Масштаб определяется числом фрагментов, а не только файлов.

## Интерфейс ноутбуков

В каждой ячейке понятное объяснение, комментарии к значимым строкам и проверяемый промежуточный результат. Поиск по новой теме не требует повторной индексации неизменённых документов.

Ноутбук оценки не обращается к endpoints, сохраняющим оценки в базе RAG, без отдельного решения. Для одиночных запросов используем пустую session_id, чтобы не загрязнять историю. Реальные побочные эффекты адаптера проверяем перед реализацией.

## Планируемая структура

```text
rag_testing/
├── README.md
├── ARCHITECTURE.md
├── docs/PLAN.md
├── notebooks/             # будущие .ipynb
├── src/                   # общие функции по мере необходимости
├── config/                # примеры настроек
├── data/examples/         # только синтетические примеры
├── data/private/          # локальные реальные таблицы
├── cache/                 # локальные индексы
└── results/               # локальные результаты запусков
```

Эта схема — первоначальный план. Фактически уже существуют `.venv/` и `golden_dataset_project/` с manifest, конфигурацией, версией корпуса и рабочим Notebook. Общие `src/`, индексы, генерация и оценка остаются будущими задачами.

## Критерии первого рабочего этапа

- Получен валидный непустой вектор ожидаемой размерности.
- Разные тексты дают осмысленно различающиеся векторы; проверены простые положительные и отрицательные пары.
- Изменение модели инвалидирует кеш.
- По теме показана подборка с точными источниками и без точных дублей.
- Человек может отметить решения и сохранить их.
- Ошибки файлов/API отображаются отдельно.
- Исходные документы не изменяются.

## Будущий контур агентов

Отдельный набор сценариев, адаптер инструментов, фиктивные ответы, трассы и оценка результата/вызовов. Разметка сценариев не смешивается с qrels поиска документов. Подробности и ограничения текущей документации Ragas — в [плане](docs/PLAN.md#8-ragas-генерация-наборов-для-агентов-и-инструментов).

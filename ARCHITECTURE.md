# Архитектура rag_testing

**Проектируемая архитектура**, а не описание уже работающего приложения. Дата: 14 октября 2026.

## Компоненты

| Компонент | Вход | Выход |
|---|---|---|
| Jupyter Notebook в VS Code | Настройки пользователя | Последовательный запуск и таблицы |
| Читатель корпуса | Локальные Markdown | Документы с метаданными |
| Подготовка текста | Документы | Фрагменты, ID, группы дублей |
| Индексатор | Фрагменты + LM Studio embeddings | BM25 и отдельный векторный кеш |
| Подборщик | Тема | Объединённый рейтинг кандидатов |
| Генератор тестов | Утверждённые фрагменты + отдельная LLM | Черновые вопросы, ответы, цитаты |
| Проверка человеком | Черновики и тексты | Версия утверждённого эталона |
| Адаптер RAG | Вопросы | Ответы, источники и контекст |
| Оценщик | Выдача + эталон | Метрики и отчёты |

Прямой зависимости от NotebookLM нет. Ragas — планируемая интеграция для генерации и оценки, а не установленная обязательная зависимость.

## Поток данных

Тема → BM25 + Giga → кандидаты → утверждение материалов → генерация тестов → проверка эталона → API RAG → сохранение выдачи → вычисление метрик.

Подготовка эталона и запуск тестируемого RAG разделены. Источники читаем; изменения исходного rag_a3 не входят в первый этап.

## Корпус и идентификаторы

Первый профиль: local_docs. Дополнительные профили:
- serving_corpus: local_docs + output_ranked + используемые эталоны с правилами загрузки чата;
- source_corpus: исходные локальные материалы + Confluence для исследования потерь предварительного отбора.

Не смешиваем эти профили в одном recall без явного обозначения области оценки.

document_id строится из нормализованного пути относительно корня корпуса; chunk_id включает document_id, границы раздела и хеш текста. corpus_version фиксирует манифест файлов и контрольные суммы. При изменении текста ID/версия меняются с сохранением связи со старым источником.

Если единица оценки RAG — полный файл, сопоставляем фрагменты разметки с ID файла для документных метрик. Нельзя сравнивать чанк и целый документ как одинаковые единицы без адаптации. Для смыслового покрытия используем фактический контекст генерации.

Дубли объединяем по установленному правилу и сохраняем все исходные пути. Не используем только basename: разные файлы могут иметь одно имя.

## Кеш и воспроизводимость

Ключ кеша включает модель, сборку/версию, параметры обработки, хеш текста и размерность. Новый embedder требует собственного индекса. Запросы и документы кодируются одной моделью с корректными разными инструкциями.

Настройки запуска: источники, корпус, модель, chunking, BM25, fusion, K, промпты, температуры, версии зависимостей и эталона. Результаты сравниваются на одинаковых версиях.

Для 700 документов достаточно локального BM25 и матрицы векторов; отдельный сервер векторной БД в первом варианте не планируется. Масштаб определяется числом фрагментов, а не только файлов.

## Интерфейс ноутбуков

В каждой ячейке понятное объяснение, комментарии к значимым строкам и проверяемый промежуточный результат. Поиск по новой теме не требует повторной индексации неизменённых документов.

Ноутбук оценки не обращается к endpoints, сохраняющим оценки в базе RAG, без отдельного решения. Для одиночных запросов используем пустую session_id, чтобы не загрязнять историю. Реальные побочные эффекты адаптера проверяем перед реализацией.

## Критерии первого рабочего этапа

- Получен валидный непустой вектор ожидаемой размерности.
- Разные тексты дают осмысленно различающиеся векторы; проверены простые положительные и отрицательные пары.
- Изменение модели инвалидирует кеш.
- По теме показана подборка с точными источниками и без точных дублей.
- Человек может отметить решения и сохранить их.
- Ошибки файлов/API отображаются отдельно.
- Исходные документы не изменяются.

# План подготовки эталонов и тестирования RAG

Дата: 14 октября 2026. Это проектируемый процесс; выполненного тестирования и готовых ноутбуков пока нет.

## 1. Цель и границы

Пользователь управляет тестами через Jupyter Notebook в VS Code и проверяет таблицы. Подбор документов, создание черновиков вопросов, отправка запросов и вычисления автоматизируются.

Раздельно проверяем:
- поиск: какие документы/фрагменты найдены;
- контекст: достаточно ли в нём сведений для ответа;
- ответ: правильность, полноту и подтверждённость источниками.

Google NotebookLM не является необходимой зависимостью. Он может помочь с черновиками, но исполняемый Python-ноутбук открываем в VS Code.

## 2. Первый практический этап: пакет документов по теме

Пользователь задаёт тему, например «Партнёр в системе А3: определение и роль», папку, модель и количество результатов.

Ноутбук:
1. Проверяет доступность папки и LM Studio, получает ID моделей.
2. Читает Markdown рекурсивно, отделяет YAML-метаданные от текста.
3. Разделяет большие документы по заголовкам с контекстом родительских разделов; не дробит повторно короткие готовые чанки.
4. Убирает точные дубли, сохраняя соответствия исходным файлам.
5. Строит BM25 с обработкой русских слов и отдельный векторный индекс Giga.
6. Объединяет ранги через Reciprocal Rank Fusion. Косинусный скор и BM25 напрямую не складываем.
7. Показывает кандидатов с путями, разделами, текстом и позициями обоих поисков.
8. Сохраняет локальную таблицу для проверки.

Числа для пилота: до 30 кандидатов, просмотр около 10–15 различных документов. Это настройки проекта, а не стандарт или гарантия полноты. Несколько результатов одного файла группируются.

На первом этапе embedding-модель ищет по смыслу. Сама она не составляет объяснения, определения и вопросы. Дополнительный LLM-отбор — следующий необязательный шаг.

## 3. Что пользователь делает руками

1. Открывает папку проекта в VS Code, выбирает Python kernel.
2. Загружает Giga в LM Studio, включает сервер.
3. Вводит тему и запускает ячейки первого ноутбука.
4. Просматривает предложенные фрагменты, принимает или отклоняет материалы.
5. Запускает генерацию по утверждённому пакету, проверяет вопросы, ответы и цитаты.
6. Запускает тестируемый RAG, затем ноутбук оценки.
7. Просматривает ошибки и спорные результаты, утверждает новую версию разметки при необходимости.

Если пакет слабый, расширяем запросы/глубину/корпус. Пользователь не выбирает заранее все файлы из сотен документов.

## 4. Ragas: генерация тестов из документов

Подход Ragas: из документов выделяются фрагменты, сущности и связи; на выбранных источниках строятся сценарии и генерируются вопросы с эталонными ответами. Есть сценарии с одним и несколькими источниками, конкретные и обобщающие вопросы. [Официальное описание](https://docs.ragas.io/en/latest/concepts/test_data_generation/rag/).

Наша адаптация:
- начинаем с одного утверждённого фрагмента;
- просим модель составить до трёх естественных вопросов, ответы и точные цитаты;
- сохраняем ID источников программно;
- проверяем наличие цитат в тексте;
- человек проверяет смысл, актуальность и достаточность подтверждений;
- позже добавляем связанные фрагменты и реальные пользовательские вопросы.

Ragas рассматриваем как возможный инструмент реализации. Первую простую генерацию можно выполнить собственным кодом. Перед интеграцией фиксируем версию Ragas и проверяем API; примеры документации не являются готовыми ячейками проекта.

Исходные подтверждения известны сразу, но они не образуют автоматически полный перечень всех релевантных документов.

## 5. Таблицы и поля

### Кандидаты документов

Одна строка на фрагмент: topic_id, document_id, chunk_id, relative_path, heading, text, bm25_rank, dense_rank, fusion_rank, duplicate_group, review_status, reviewer_note.

### Вопросы

Одна строка на вопрос: question_id, product, question, reference_answer, query_type, origin, corpus_version, review_status.

origin различает синтетический вопрос и реальный пользовательский. query_type: single_source, multi_source, unanswerable. Вопросы без ответа проверяются отдельно.

### Разметка источников

Одна строка на пару вопрос/фрагмент: question_id, chunk_id, relevance, evidence_quote, supports_claim, assessed_by, review_status.

relevance: relevant, not_relevant, unjudged. Храним отрицательные решения и непроверенные материалы, а не только положительный список. Неизвестный ID не объявляем автоматически нерелевантным.

### Результаты запуска

run_id, question_id, response, retrieved_ids, ranks, retrieved_contexts, generation_contexts, model_ids, settings, corpus_version, latency, error, metrics.

Важно различать полный найденный фрагмент и текст, реально переданный генератору после обрезки.

## 6. Метрики и полнота эталона

Пусть G — множество релевантных ID, R_K — первые K результатов по установленному правилу дедупликации.

- Precision@K = число релевантных результатов в первых K / K. Если система вернула меньше K, отдельно фиксируем это и выбранное правило; не меняем знаменатель молча.
- Recall@K = |R_K ∩ G| / |G|.
- Если G пусто, recall не определён; тесты без ответа получают отдельные показатели.
- Ошибка запроса не становится нулевой метрикой без отдельной отметки.
- Усредняем по вопросам и показываем разрезы по темам.

Обе метрики требуют разметки. Для precision можно разметить выданные результаты после запуска; для recall нужно знать также пропущенные источники.

Для расширения эталона объединяем кандидатов нескольких поисков и размечаем общий пул. Такой pooling используется в TREC. [NIST/TREC](https://trec.nist.gov/howto.html). Recall по неполному пулу обозначаем как recall относительно размеченного набора.

Новые полезные документы размечаем отдельно, фиксируем новую версию эталона и пересчитываем все сравниваемые запуски на ней.

### Отдельные показатели Ragas

LLM Context Recall проверяет покрытие утверждений эталонного ответа найденным контекстом; это не recall по всем документам. Context Precision учитывает порядок релевантных результатов и отличается от простой доли полезных элементов. ID-based варианты сравнивают идентификаторы. [Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/), [Context Precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/).

LLM-оценки сохраняем с моделью, промптом и версией. Проверяем их согласованность с ручной оценкой на пилоте.

## 7. Запуск тестов

Ноутбук читает утверждённые вопросы и обращается к API RAG. В запрос передаём вопрос и продукт; эталонный ответ и список источников не передаём.

Каждый одиночный вопрос выполняется без истории. Многошаговые диалоги — отдельные тесты. Нужны реальные ID, порядок и тексты найденных источников. Если текущий API этого не предоставляет, проектируем отдельный адаптер; изменения RAG согласуются отдельно.

По просмотренному коду текущего rag_a3 TOP_K_FINAL = 10, хотя README описывает 5. Значение проверяется и фиксируется для каждого запуска. Измеряем отдельно кандидатов до и результаты после реранжирования, если они доступны.

В существующей SQLite evaluations было шесть записей по двум темам; это начальные примеры, а не достаточный benchmark. Уже имеющиеся эталонные документы входят в корпус чата: отмечаем их происхождение и отдельно проверяем сценарии по исходной документации.

## 8. Ragas: генерация наборов для агентов и инструментов

**Обязательное направление дальнейшего развития.** Страница [Testset Generation for Agents or Tool use cases](https://docs.ragas.io/en/latest/concepts/test_data_generation/agents/) на дату проверки содержит анонс разработки средств синтетической генерации, но не описание готового генератора. Не обещаем такую функцию как уже доступную.

Предлагаемая нами схема сценария:
scenario_id, task, initial_state, available_tools, expected_calls, expected_arguments, order_constraints, expected_result, forbidden_actions, mocked_tool_responses, review_status.

Примеры синтетических сценариев:
- найти документ через search_documents, затем прочитать его через read_document;
- уточнить неоднозначное название сущности;
- обработать пустую выдачу или недоступный инструмент;
- выполнить цепочку вызовов с передачей найденного ID;
- не вызывать инструмент, когда задача решается имеющимся контекстом.

Сохраняем трассу вызовов, параметры, ответы инструментов и итог. При нескольких допустимых путях задаём ограничения и ожидаемый результат, а не единственную жёсткую цепочку. Первые тесты используют фиктивные инструменты и данные.

Метрики для исследования: Tool Call Accuracy, Tool Call F1, Agent Goal Accuracy, Topic Adherence. Доступность и точную семантику проверяем в выбранной версии. [Метрики Ragas](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/).

Этот этап расширяет проект, но не требуется для первого пакета документов.

## 9. Очерёдность реализации

1. Проверка Giga GGUF и минимального поиска.
2. Ноутбук подбора и локальная таблица кандидатов.
3. Проверка пакета на теме «партнёр».
4. Генерация первых 10 черновых вопросов; утверждение человеком.
5. Расширение разметки и фиксация корпуса.
6. Адаптер RAG и метрики, проверка на двух вопросах.
7. Расширение примерно до 30 вопросов и отдельный набор для настройки.
8. Исследование сценариев агентов/инструментов.

Количество вопросов — стартовые ориентиры; они не доказывают статистическую надёжность. Тестовую часть не используем для подгонки настроек.

## 10. Модели и нерешённые вопросы

Выбрана для пилота Giga-Embeddings-instruct-480M-0826, GGUF Q8_0, найденная в LM Studio. [Оригинал](https://huggingface.co/ai-sage/Giga-Embeddings-instruct-480M-0826), [сборка](https://huggingface.co/rad0main/Giga-Embeddings-instruct-480M-0826-GGUF).

Предстоит проверить API ID, mean pooling, двунаправленное внимание, размерность 1024, формат инструкции запросу и отсутствие скрытого обрезания длинных текстов. Наличие сборки в каталоге не подтверждает корректность инференса.

Отдельно выбираем генератор вопросов и оценщик, отличные от тестируемой модели. Пока конкретные модели не утверждены. Независимость моделей уменьшает общий перекос, но не заменяет проверку человеком.
